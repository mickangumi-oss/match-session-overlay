# 対戦データ比較仕様案

状態: `FIELD_MAP_CONFIRMED_IMPLEMENTATION_GO`

現在の実装ゲート: `UI_IMPLEMENTATION_GO_PENDING_QA`（`round_results`のfield map確定。UI実装はGO、QA・ローカルビルド・コミット・公開は各ゲート完了まで保留）

対象: Match Session Overlay v1.11.1 の対戦履歴から開く、選択相手とのデータ比較。

この文書は内部運用用のPlanner仕様です。実装、ビルド、コミット、公開の承認ではありません。

## 目的

完了した対戦を起点に、自分と選択した相手のデータを同じ条件で並べ、ユーザーが自分で振り返りのきっかけを見つけられるようにする。相手の弱点、試合前の攻略、予測、勝ち筋、集計値からの因果断定は目的にしない。

## 対象ユーザーと利用環境

- 対象ユーザー: 自分の対戦履歴を確認する利用者。
- 起点: 対戦履歴の行選択 → 相手プロフィール（参考情報） → `データ比較`。
- 表示: 別Windowsウィンドウではなく、既存アプリ内の全画面パネル。
- データ: 自分の公式プロフィールと、選択行の相手プロフィール。
- 現行基準: v1.11.1の対戦履歴・相手プロフィール表示。既存の凍結試作画面は現行仕様としない。

## 確定要件

### 導線・状態保持

1. 相手プロフィール内に`データ比較`ボタンを追加する。
2. 相手プロフィール右上に閉じるボタンを置き、閉じると行選択を解除する。
3. 比較パネルを閉じて戻ると、フィルター、スクロール位置、選択行、相手プロフィールを保持する。
4. 押下後は即時にヘッダーとローディング状態を表示し、自分・相手のデータを並行取得する。
5. セクション単位で順次表示する。片側または一部の失敗で全画面を閉じない。
6. 表示中は自動更新しない。更新ボタンによる明示更新だけを行う。
7. 比較対象は選択行の相手IDへ固定する。相手切替後の遅延応答は破棄する。

### 見出し・パネル

- `バトル傾向：過去100戦平均`
- `ラウンド傾向：取得できた対戦履歴を集計`
- 比較グラフは中央の項目名から左右へ伸びる対称型横棒。
- 左側は自分（青系）、右側は相手（紫系）。色だけで意味を判断させない。
- 実数または割合を表示する。良否色、総合点、評価、助言、順位付けは表示しない。
- 項目は折りたたまず、全項目を縦スクロールで確認できるようにする。
- 旧draftの直接対戦勝率ドーナツ、勝率カード、スコア・評価カードは比較パネルへ含めない。勝率は既存履歴の別表示として扱う。

### バトル傾向

Buckler公式 `PLAY > 実績` のプレイヤー全体「過去100戦平均」を、自分と相手で同じ項目同士比較する。単一試合の値とは区別する。

対象項目は、ユーザーが確認した公式画面の次の範囲に限る。

- ドライブゲージ使用実績
- ドライブリバーサル
- ドライブパリィ
- ドライブインパクト（自分の使用／対戦相手の使用）
- SAゲージ使用割合
- スタン
- 投げ
- 壁際

勝率、キャラクターLP/MR、プレイポイント、対戦数、エンジョイ等、別タブの値はこの比較へ混在させない。

### ラウンド傾向

- 本人が獲得したラウンドを母数に割合を主表示し、件数を補足する。
- 自分・相手それぞれの集計試合数と獲得ラウンド数を表示する。
- 既存履歴は推測補完しない。公式から再取得できる範囲だけ同じ方式で補完する。
- 今後取得する履歴では、対象プレイヤー側コードと順序をサニタイズして`round_results`を保持する。生ログ全体は保存しない。

## データ・プライバシー契約

- 自分・相手は同じ表示項目、期間、モード、ACT、キャラクター範囲、単位で比較する。
- 欠損、未確認、取得不能は推測変換せず、`—`、`PARTIAL`、`UNAVAILABLE`等で表示する。0埋めしない。
- `LOADING`、`READY`、`PARTIAL`、`INSUFFICIENT_SAMPLE`、`UNAVAILABLE`、`ERROR`を区別する。
- 内部Source URL、Locale、内部ユーザーID、Cookie、認証情報、生ログは画面・QA成果物へ出さない。
- `round_results`は公式field mapを確認済み。公式コード表記を保持し、日本語の技名展開は推測しない。

### キャラクター名のlocale解決

- 取得したキャラクター名が選択中localeの正式ラベルであれば、その値を優先する。
- 既存履歴などで日本語・別localeのラベルしかない場合は、確認済みの`characterId`→選択中locale辞書を使う。
- 辞書にないIDは既知名を推測せず、非ローカライズ文字列が取得できた場合だけそれを保持し、それ以外は`#ID`（IDもない場合は`—`）とする。
- このresolverは管理画面、MATCH LIST、相手プロフィール、比較画面、FRIENDS/FOLLOWING、通常ウィンドウで共通利用する。

### 確定field map（サニタイズ済み）

- 対象パス: `props.pageProps.replay_list[].player1_info.round_results`、`props.pageProps.replay_list[].player2_info.round_results`。
- 観測: 10試合・20配列、配列長2〜3、数値型。観測コードは`0,1,2,5,6`。
- コード契約: `0`=no-result marker、`1`=`V`、`2`=`C`、`3`=`T`、`4`=`D`、`5`=`OD`、`6`=`SA`、`7`=`CA`、`8`=`P`。
- SA1/SA2/SA3のラウンド獲得分類はできない。SAは単一コードとして扱う。
- `V/C/T/D/OD/SA/CA/P`の正式な日本語展開はpayloadから確認できないため、公式コード表記を表示・保存する。
- 欠損、空配列、未知、不正値は`unknown`／`UNAVAILABLE`等へ倒し、`0`を獲得ラウンドへ数えない。
- 公式取得テンプレートは`/_next/data/{buildId}/{locale}/profile/{id}/battlelog.json?page=...`。実ID、URL、生ログは成果物へ残さない。

### Stage 1 実施結果（2026-09-08）

- Engineer2が内部保持の限定実装を完了。対象は配列の順序保持、0〜255の整数サニタイズ、未知値の推測禁止、旧履歴の非補完。
- 初回Stage1再実行（旧SHA）は比較UI candidateのSHA drift検知時に無効化。コード契約の独立QAはfocused 22/22、`pnpm check` 124/124、`pnpm lint` exit 0、`git diff --check` exit 0だが、candidate版では再実行が必要。
- 公式field mapはSol確認済み。インストール済みアプリの旧経路はhome HTTP 200／battlelog HTTP 403だったため、アプリ経路の取得実装は承認テンプレートへ切り替える必要がある。
- Stage 1の変更にはUI比較画面の受入を含めず、ローカルビルド・コミット・公開は未実施。
- 独立QAで検出した、未知コード・不正値を勝敗へ混入させる不整合はSol方針で修正済み。現行SHAで再確認済みだが、チケットはUI・パッケージ未確認のため`Fixed`止まりで`Closed`にはしない。
- Sol決定: 勝敗派生に使えるのはprimitive integer `1..8`だけ。`0`は非勝利、未知値・不正値は勝敗に影響させず、検証済みの別result fieldがない場合はfail-closedとする。診断用の未知コード保持は継続する。
- QA再確認後、空配列・片側空配列・欠損側はいずれも`result=unknown`となることを確認。空配列の仕様は追加の未解決事項ではない。
- Stage1固定SHA（比較UI candidate変更前の履歴値）は参考記録であり、現行candidateのQA根拠には使用しない。candidate凍結後に対象ファイルSHAを再固定する。

## 受入条件案

1. 選択行から比較を開き、閉じると選択状態とプロフィール表示が仕様どおり戻る。
2. 選択相手以外のデータが混入せず、相手切替後の遅延応答が破棄される。
3. バトル傾向は公式`PLAY > 実績`の同一項目・同一期間を自分／相手で並べる。
4. ラウンド傾向は本人側の獲得ラウンド母数を明示し、割合と件数を分けて表示する。
5. 取得中、片側失敗、両側失敗、母数不足、部分欠損、再試行、明示更新を確認する。
6. 不明値を0や評価へ変換せず、取得済みセクションを維持する。
7. 横overflow、文字重なり、文字切れを発生させず、狭幅でも全項目を縦スクロールできる。
8. 既存の対戦履歴、相手プロフィール6項目、ACT、取得時点を削除しない。
9. `round_results`は確定field mapのコード表記を使い、未知・不正・空・欠損をREADY扱いにしない。PLAY内部field path未検証項目も同様にREADY扱いにしない。
